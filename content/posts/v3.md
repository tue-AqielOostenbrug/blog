### Learning commands
IRC actually has hundreds of commands and parameter pecularities. For a good guide see the documentation at [ircdocs.horse](https://ircdocs.horse/) or the official documentation at [https://www.rfc-editor.org/rfc/rfc1459](https://www.rfc-editor.org/rfc/rfc1459). Luckily, for my simple client, there were only three stages that I felt I needed to concern myself with: Authentication, channel navigation, and communication.

For authentication, I decided to use the following commands to login:
- `PASS <password>`: Submits your password to the server
- `NICK <nickname>`: Submits your nickname to the server
- `USER <username> 0 * :<realname>`: Submits your username and realname to the server

It is important that this stage happens first after connecting to the server. If not, the client will not be serviced and won't even be allowed to authenticate if the time-out is reached. Note that password is not always essential as many servers allow clients to connect without full authentication.

For navigation, I decided to restrict myself to the following three commands:
- `JOIN <channel>`: this allows you to join a channel (kind of like a groupchat with a specific name in the server)
- `LIST`: show you a list of all available channels on the server
- `PART <channel>`: removes you from the specified channel

Then finally, for communication, I only focussed on one command:
- `PRIVMSG <target> <msg>`: Sends a msg to the target ( channel or nickname) you specified.
### Testing commands
Now that I learned some important IRC commands, I needed to test them. The easiest way to experience the IRC protocol without a full client is to connect to an IRC server using `telnet` or `netcat`.

On Arch you can install `telnet` by running:
```bash
sudo pacman -Sy inetutils
```
Then you can connect to the server using:
```bash
telnet <server address> <port>
```
Then you can simply write the commands in the terminal and press enter to send the commands to the server.
However, please note that `telnet` is not practical to use for real IRC communication because it does not support TLS encryption. This allows malicious actors to read and  modify the content of any message that you or the server send if they can manage to position themselves between the client and the server.

Alternatively, you can use netcat. Installing `netcat` on Arch goes as follows:
```bash
sudo pacman -Sy openbsd-netcat
```
**Please note that the `openbsd-netcat` package has been flagged as out of date as of 08-03-2026.**

Connecting to the server using `netcat`:

```bash
nc <server address> <port>
```
You need to watch out since netcat only sends `\n` by default. As such, you need to add `\r` for some servers to function properly because the IRC protocol specifies that all lines should be ended with  a `\r\n` and old servers mainly still need this constraint to hold to parse properly.

## IRC sockets

Now that I felt like I was getting back into the game, I could finally properly tackle the IRC socket communication in C. Eventually, combining my new knowledge with the [C devdocs](https://devdocs.io/c/) and relevant man pages I managed to get it working. However, I found myself in a situation were the server would ignore occasionally my commands. After debugging, I concluded that this seemed to happen due to one of two reasons.

1. I didn't wait enough between sending commands. This can be resolved by adding a time delay after every `write(fd)`
2. Commands were not properly parsed by the server. This could be resolved by explicitly adding a `\r\n` after each command.

Additionally, I was often rejected by the server because the nickname was already registered. This happens because after registering a nickname and then leaving the server, it takes a while for the server to realize the user is gone if the user doesn't explicitly notify the server.

### Acceptance
There were no shortcuts. I decided to read through the documentation of the driver and along the way read up on the underlying SPI and TFT protocols. Additionally, I searched for the original GitHub repository on which the manufacturer based their implementation. After comparing the Jingcai implementation against the original Espressif version (see the [lvgl esp32 driver repository](https://github.com/lvgl/lvgl_esp32_drivers)), I realized that the solution was quite simple all along. The order of the conversion from raw coordinates to effective coordinates was supposed to happen after the orientation correction. This looks as follows:

			uy = t;

## Wrap-up
During this project there were many learning experiences which I couldn't fit into this blog post. Moreover, the way in which I presented this journey above is not entirely correct. Many times, I had to take many steps back to go one step forward. However, regardless of all of that I hope that this post gave a good insight into my somewhat arduous but fun journey. Although, much this project was out of my initial expectations, I think that it forced me to become a **better embedded systems engineer**:

- [x] **Become an advanced C programmer**: \
To show an advanced proficiency of C/C++ programming and expertise with an embedded system, I went back to the basics. I read important foundational books, followed a foundational course and learned more about how to resolve important questions using `man-pages` and `devdocs`. Additionally, I watched videos on the art of Structured Programming and embedded systems programming. I then applied this knowledge by programming in C for an ESP32 where I programmed sockets, improved my usage of popular C build systems and the Espressif libraries. This combination of a better theoretical foundation and the practical experience, improved my programming skills and expertise with embedded systems, increasing my profiency to an advanced level.
- [x] **Produce a complete embedded system** \
During this journey, I went through the entire development cycle. Together with my supervisor I designed an embedded system by choosing a microcontroller, charging circuit and battery. I implemented the IRC client using the industry standard protocol and evaluated the results using unit testing and Docker. I documented my code and produced an online wiki for future developers. This process I documented in this blog post, [IRC Client repository](https://github.com/tue-AqielOostenbrug/qmesg) and [ESP32 Interface repository](https://github.com/tue-AqielOostenbrug/esp32-interface).
- [x] **Stay organized**: \
I used Scrum to integrate features in a step-by-step manner such that my supervisor/stakeholder could provide valuable feedback due to the frequent iterations, resulting in quick and effective feedback loops. Concretely, I planned future tasks and tracked their progress on a Scrum board where possible and did weekly stand-ups with my supervisor to discuss what I did, what I was planning to do and what are my blockers. In addition, I held short sprint reviews to collect feedback on demo's and sprint retrospectives to what went well, what didn't and how I wanted to change. This kept my progress somewhat streamlined, even throughout the inevitable roadbumps.
